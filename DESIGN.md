# LuxeKey --- Design Document

## 1. Overview

LuxeKey is a hotel booking portal prototype created for a Java Developer
Intern assessment. It provides a React user interface backed by a Spring
Boot REST API and a MySQL database.

The main workflow is:

1.  Browse hotels.
2.  Search by location.
3.  Select check-in and check-out dates.
4.  View rooms available for those dates.
5.  Review the calculated stay amount.
6.  Submit a booking.
7.  Receive a unique booking reference and confirmation status.
8.  Retrieve or cancel a booking using its reference and customer email
    through the backend API.

The implementation focuses on the booking flow and date-overlap rules.
Authentication, payment, and operational hotel-management workflows are
outside the current prototype scope.

## 2. Architecture

The application uses a simple three-layer architecture.

``` text
React + Vite frontend
        |
        | HTTP requests (Axios)
        v
Spring Boot REST controllers
        |
        v
Service layer
        |
        v
Spring Data JPA repositories
        |
        v
MySQL database
```

### Frontend

-   React manages the hotel list, destination, dates, selected hotel,
    available rooms, customer form, and booking confirmation state.
-   Axios calls the backend REST endpoints.
-   CSS provides the LuxeKey visual style: ivory backgrounds, deep green
    hero section, terracotta accents, and serif display typography.

### Backend

-   Controllers expose hotel and booking endpoints.
-   Services contain booking validation, availability, pricing, and
    cancellation logic.
-   Repositories use Spring Data JPA to query and persist entities.
-   Hibernate maps Java entities to MySQL tables.

### Relationships

-   A hotel can have multiple rooms.
-   A room belongs to one hotel.
-   A customer can have multiple bookings.
-   Each booking references one customer and one room.
-   Hotel amenities are stored as an element collection.

The current sample data creates five hotels, each with one Deluxe Room.
These are fictional records used for development and demonstration.

## 4. Database design

Hibernate creates/updates the schema using the configured JPA DDL mode.

Conceptual tables:

-   `users`
-   `hotel`
-   `hotel_amenities`
-   `room`
-   `booking`

Important booking columns:

  Column              Description
  ------------------- -----------------------------------------
  id                  Primary key
  booking_reference   Unique human-readable booking reference
  check_in            Arrival date
  check_out           Departure date
  total_price         Server-calculated total
  status              `CONFIRMED` or `CANCELLED`
  room_id             Booked room
  customer_id         Customer who made the booking

The booking reference is generated by the backend using a UUID-derived
value with an `LK-` prefix.

## 5. API design

All endpoints use the `/api` base path.

  ------------------------------------------------------------------------------------------------------------
  Method                  Route                                                        Description
  ----------------------- ------------------------------------------------------------ -----------------------
  GET                     `/hotels`                                                    Return approved hotels

  GET                     `/hotels/{id}`                                               Return one approved
                                                                                       hotel

  GET                     `/hotels/search?location={location}`                         Search hotels by
                                                                                       location

  GET                     `/hotels/{id}/rooms`                                         Return rooms for a
                                                                                       hotel

  GET                     `/hotels/{id}/availability?checkIn={date}&checkOut={date}`   Return rooms without a
                                                                                       conflicting confirmed
                                                                                       booking

  POST                    `/bookings`                                                  Create a booking using
                                                                                       roomId, customerId,
                                                                                       checkIn, checkOut
                                                                                       request parameters

  GET                     `/bookings/{reference}?email={email}`                        Retrieve a booking

  PUT                     `/bookings/{reference}/cancel?email={email}`                 Cancel a booking
  ------------------------------------------------------------------------------------------------------------

Dates are represented as ISO local dates (`YYYY-MM-DD`). The current
booking creation endpoint accepts request parameters rather than a JSON
DTO.

## 6. Booking logic

### Date validation

A booking is rejected when:

-   Check-in or check-out is missing.
-   Check-in is in the past.
-   Check-out is not after check-in.

### Price calculation

The backend calculates:

``` text
numberOfNights = daysBetween(checkIn, checkOut)
totalPrice = room.price × numberOfNights
```

Example:

``` text
Room price = ₹3,500 per night
Check-in = 8 December
Check-out = 11 December
Number of nights = 3
Total = ₹3,500 × 3 = ₹10,500
```

The frontend displays an estimate, but the backend calculates and stores
the authoritative total.

### Availability and overlapping stays

A confirmed booking conflicts with a requested stay when:

``` text
existing.checkIn < requested.checkOut
AND existing.checkOut > requested.checkIn
```

This is the standard half-open date-range overlap check. It allows
back-to-back reservations: if one guest checks out on 10 December,
another may check in on 10 December.

Only bookings with `CONFIRMED` status block availability. A booking
marked `CANCELLED` is excluded from the conflict query and therefore
releases the room dates.

### Preventing simultaneous overbooking

During booking creation, the service obtains a pessimistic write lock on
the selected room row inside a transaction. It then checks for a
conflicting confirmed booking and saves the new booking if no conflict
exists.

This serializes competing booking attempts for the same room, provided
the database uses transactional row locking (as with InnoDB). The
conflict check is performed after acquiring the lock.

### Cancellation

The cancellation flow finds a booking using its reference and customer
email, locks its room, verifies that the booking is still confirmed, and
changes its status to `CANCELLED`.

The availability query ignores cancelled bookings, so those dates become
bookable again.

## 7. User interface

The interface is designed around a premium hospitality identity:

-   Brand: LuxeKey
-   Palette: ivory, deep green, terracotta, muted sand
-   Typography: Playfair Display for editorial headings and DM Sans for
    interface text
-   Layout: horizontal navigation, destination/date search, hotel cards,
    room details, and a booking confirmation panel

The booking confirmation displays the unique booking reference, total
amount, and status.

## 8. Assumptions and trade-offs

-   A `Room` record represents a bookable room type with a single
    capacity and nightly price. The current prototype treats that room
    record as one unit of availability; it does not model multiple
    physical rooms or inventory counts.
-   Sample hotel data is seeded only when the hotel table is empty.
-   A demo customer record is created manually in MySQL. The React
    frontend currently uses a configured customer ID.
-   The booking form collects name and email, but the current backend
    booking operation identifies the customer by ID. Full customer
    registration and identity verification remain unfinished.
-   No payment is collected. A booking is marked confirmed immediately
    when saved.
-   The backend uses basic runtime exceptions in some failure paths; a
    production version should add structured exception handling and
    validation responses.
-   Monetary fields currently use `double`; a production implementation
    should use `BigDecimal`.
-   No authentication, authorization, hotel-manager approval workflow,
    or admin dashboard is implemented, despite role fields existing in
    the User entity.
-   The project is intended for local assessment demonstration, not
    production deployment.

## 9. Testing performed manually

The following checks were performed locally:

-   Backend Maven compilation completed successfully.
-   Spring Boot started on port 8080 and connected to MySQL.
-   The hotel API returned hotel details and amenities.
-   The availability API returned the Deluxe Room for unbooked dates.
-   A booking was saved in MySQL with a generated reference, calculated
    total, and `CONFIRMED` status.
-   After a booking, the same room was no longer returned for
    overlapping dates.
-   A booking for a non-overlapping date range was successfully created
    and displayed in the frontend confirmation screen.

Automated test coverage should be added for date validation, pricing,
overlap boundaries, cancellation, and concurrent requests.

## 10. Future improvements

1.  Add customer registration and authentication; remove the hard-coded
    customer ID.
2.  Bind customer name and email to the persisted customer record.
3.  Use `BigDecimal` for all monetary calculations.
4.  Add DTOs, bean validation, and centralized API exception handling.
5.  Model physical room inventory or room quantities instead of treating
    one room-type row as one unit.
6.  Add automated unit and integration tests.
7.  Add a frontend booking lookup and cancellation page.
8.  Add a distinct surprise feature and document its behavior once
    implemented.
9.  Move credentials to environment variables and prepare production
    configuration.
